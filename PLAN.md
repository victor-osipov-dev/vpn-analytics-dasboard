# PROMPT: Разработка NetScope — десктопного дашборда мониторинга интернета, VPN и сетевых блокировок

## 1. Твоя роль

Ты — senior full-stack разработчик, системный программист Rust, сетевой инженер и архитектор desktop-приложений.

Твоя задача — **разработать полноценное работающее приложение NetScope**, предназначенное для мониторинга интернета, выявления сетевых ограничений, анализа доступности сервисов и сравнения подключений с VPN и без VPN.

Не ограничивайся созданием интерфейса, заглушек или демонстрационной версии.

Реализуй работающее приложение с реальными сетевыми проверками, хранением результатов, обработкой ошибок, автоматической диагностикой и современным интерфейсом.

Самостоятельно принимай обоснованные технические решения. Если функция требует повышенных привилегий или системных возможностей, сначала реализуй безопасный доступный вариант, затем документируй ограничения.

Не выдавай неподтверждённые функции за работающие.

## 4. Критически важная функция: DIRECT/VPN Monitoring

Это одна из главных возможностей приложения.

Пользователь должен видеть состояние доступности сервисов одновременно по двум независимым маршрутам:

**DIRECT** — прямое соединение через физический интернет, минуя системный прокси и VPN, когда это технически возможно.

**VPN** — соединение через текущий VPN, TUN или прокси.

Для каждого ресурса показывать результаты двух маршрутов.

Пример:

| Сервис | DIRECT | VPN |
|---|---|---|
| Сервис A | Доступно | Доступно |
| Сервис B | Недоступно | Доступно |
| Сервис C | Замедлено | Доступно |
| Сервис D | Доступно | Недоступно |
| Сервис E | Ошибка DNS | Доступно |

Это демонстрационные данные.

### 4.1. Типы подключений

Реализуй распознавание:

1. Прямого подключения через Wi-Fi/Ethernet.
2. Системного HTTP-прокси.
3. Системного HTTPS-прокси.
4. SOCKS5-прокси.
5. SOCKS5 с удалённым DNS-разрешением.
6. Автоматической конфигурации прокси через PAC/WPAD.
7. TUN/TAP VPN.
8. Полнотуннельного VPN.
9. Split-tunneling VPN.
10. WireGuard-совместимых сетевых интерфейсов.
11. Других VPN-интерфейсов, предоставляемых Windows.

Не пытайся распознавать конкретный VPN только по названию сетевого адаптера.

Используй сочетание данных об интерфейсах, маршрутах, системных прокси, шлюзах и фактическом прохождении тестовых запросов.

PAC/WPAD и Windows proxy bypass rules должны учитываться корректно. Если полноценная поддержка PAC пока не реализована, честно обозначай ограничение.

### 4.2. Network Route Manager

Создай модуль `NetworkRouteManager`.

Он должен:

- Определять активные физические интерфейсы.
- Определять виртуальные интерфейсы.
- Анализировать IPv4/IPv6 route table.
- Находить default gateway.
- Определять активный DNS.
- Получать системные proxy settings.
- Определять возможный TUN-интерфейс.
- Отслеживать изменения сетевой конфигурации.
- Определять доступные маршруты для диагностики.
- Классифицировать VPN как proxy-based, tunnel-based, mixed или unknown.
- Поддерживать несколько VPN одновременно.
- Не считать наличие виртуального интерфейса доказательством работающего VPN.

Дополнительно сохранять network context каждого измерения.

### 4.3. DIRECT Engine

DIRECT Engine должен выполнять запросы без использования HTTP/SOCKS-прокси.

Требования:

- Отключать неявное использование системного proxy в HTTP-клиенте.
- Использовать явную DNS-стратегию.
- Поддерживать IPv4 и IPv6.
- Определять физический интерфейс.
- По возможности задавать локальный исходящий адрес и интерфейс.
- Проверять фактический внешний IP через доверенные контрольные endpoints.
- Не считать успешное привязывание сокета гарантией обхода TUN.
- Определять случаи, когда VPN или firewall принудительно перехватывает весь трафик.

**Критическое правило:** нельзя называть измерение DIRECT, если не подтверждено, что оно прошло вне VPN.

При включённом TUN Windows может направлять весь трафик через VPN, даже если HTTP-прокси отключён.

Поэтому реализуй подтверждение фактического egress-маршрута.

Если независимая проверка невозможна, показывай:

`DIRECT: маршрут недоступен / не подтверждён`

Не отключай VPN автоматически.

Не меняй системную таблицу маршрутизации без явного разрешения пользователя.

Не отключай VPN kill switch и не обходи защитные политики пользователя.

### 4.4. VPN Engine

Реализуй:

**Proxy mode:**
- HTTP/HTTPS proxy.
- SOCKS5.
- Явная настройка proxy endpoint.
- Поддержка proxy authentication с безопасным хранением учётных данных.
- Удалённое DNS-разрешение для SOCKS5, где поддерживается.
- Учет системных исключений и PAC.
- Проверка доступности proxy endpoint.

**TUN mode:**
- Обнаружение виртуального интерфейса.
- Определение маршрута через VPN.
- Выполнение проверок через туннель.
- Подтверждение внешнего IP.
- Раздельный учёт IPv4 и IPv6.
- Обнаружение возможных DNS-утечек и split-tunneling.

Разделяй понятия «VPN обнаружен», «VPN подключён», «маршрут доступен» и «измерение подтверждённо прошло через VPN».

### 4.5. Проверка реального маршрута

Для обоих маршрутов хранить:

- Заявленный режим: DIRECT/VPN.
- Фактически определённый маршрут.
- Внешний IP.
- Используемый интерфейс.
- Предполагаемый ASN.
- DNS resolver.
- IP family.
- Тип proxy/VPN.
- Уровень достоверности маршрута.
- Причину, если маршрут не подтверждён.

Проверка внешнего IP должна выполняться через несколько независимых HTTPS endpoints с возможностью самостоятельной настройки адресов.

Не сохраняй публичный IP пользователя в облако автоматически.

При совпадении внешних IP DIRECT и VPN не делай автоматический вывод, что VPN не работает: возможны split tunnel, прозрачный прокси и другие сетевые конфигурации.

Для достоверности сопоставляй IP с маршрутами, интерфейсами и результатами контрольных проверок.

### 4.6. Режимы мониторинга

В настройках должны быть:

- Только DIRECT.
- Только VPN.
- DIRECT + VPN одновременно.
- Автоматический режим.

В автоматическом режиме приложение определяет, какие маршруты фактически доступны.

Проверки двух маршрутов должны иметь отдельные тайм-ауты, независимые соединения, DNS-контексты и историю.

Не допускай общего пула HTTP-соединений, который может привести к смешиванию маршрутов.

## 5. Модуль диагностики сети

Реализуй независимые диагностические модули.

### DNS Probe

- A и AAAA.
- Тайминги.
- NXDOMAIN/SERVFAIL/timeout.
- Ответ системного DNS.
- Ответ контрольного DNS при доступности.
- Сравнение ответов.
- DNS over HTTPS как дополнительный режим.
- Разделение локального и удалённого DNS при работе через прокси.

### TCP Probe

- TCP connect.
- Время подключения.
- Timeout.
- Connection refused.
- Connection reset.
- Отслеживание фактического исходящего интерфейса, когда это возможно.

### TLS Probe

- TLS handshake.
- TLS version.
- Сертификат.
- SNI.
- Этап возникновения ошибки.
- Timeout/reset.
- Ошибки валидации сертификатов.

Не отключай проверку TLS-сертификатов для штатных измерений.

### HTTP Probe

- HTTP status.
- Redirect chains.
- Time to first byte.
- Total duration.
- Content fingerprint.
- Наличие страницы блокировки.
- Ошибки соединения.
- HTTP/2 при поддержке.

### Performance Probe

- RTT.
- Jitter.
- Packet loss, если методика позволяет его обоснованно измерять.
- TCP connection latency.
- Изменение времени ответа.
- Throughput через контролируемые endpoints.
- Выявление устойчивого замедления.

Не выполняй тяжёлые тесты пропускной способности автоматически слишком часто.

### QUIC Probe

На втором этапе:
- HTTP/3.
- UDP/443.
- QUIC handshake.
- Сравнение поведения TCP и UDP.

## 6. DPI и анализ блокировок

Создай модуль `RestrictionAnalyzer`.

Он должен выявлять признаки:

- DNS-фильтрации.
- IP-блокировки.
- TCP reset.
- TLS/SNI-фильтрации.
- HTTP-фильтрации.
- Частичной доступности.
- Возможного ограничения QUIC.
- Устойчивого замедления.
- Локальных неполадок.
- Глобальной недоступности сервиса.
- Недостаточности измерений для вывода.

РКН и ТСПУ учитывать как часть предметной области, но **не утверждать, что конкретная ошибка вызвана РКН, без независимого подтверждения**.

Каждый диагноз должен содержать:

- Тип проблемы.
- Уровень уверенности.
- Список технических признаков.
- Возможные альтернативные причины.
- Время обнаружения.
- Использованный маршрут.
- Сведения о контрольном измерении.

Не использовать фиктивные проценты уверенности. Начни с объяснимой оценки: low, medium, high, unknown.

Особое внимание удели сравнению DIRECT и VPN.

Примеры:

- DIRECT недоступен, VPN доступен — возможное локальное ограничение, но не доказательство DPI.
- DIRECT имеет ошибки TLS, VPN работает — признак, требующий дальнейшей проверки.
- Оба маршрута недоступны — возможно, сбой сервиса, проблемы общей инфраструктуры или обеих сетей.
- DIRECT работает, VPN нет — вероятная проблема VPN, его маршрутизации или выходной сети.
- Оба работают, но DIRECT значительно медленнее — возможная деградация; для вывода о фильтрации требуются дополнительные измерения.

## 8. Разделы приложения

Реализуй навигацию:

1. **Обзор** — состояние интернета, DIRECT/VPN, основные показатели.
2. **Сервисы** — таблица доступности ресурсов.
3. **Диагностика** — ручные DNS/TCP/TLS/HTTP проверки.
4. **DPI / ограничения** — признаки фильтрации, объяснения диагнозов.
5. **Маршруты** — интерфейсы, VPN, DNS, gateway, внешние IP.

7. **События** — блокировки, восстановления, сетевые изменения.
8. **Настройки** — интервалы, тайм-ауты, прокси, список ресурсов, экспорт.

В разделе «Маршруты» создай схематическую визуализацию:

Компьютер → физическая сеть → интернет

Компьютер → системный прокси → выходной сервер → интернет

Компьютер → TUN → VPN endpoint → интернет

Схема должна отображать обнаруженные и подтверждённые элементы, а не выдумывать сетевую топологию.

## 11. Безопасность и конфиденциальность

Обязательные требования:

- Local-first.
- Никакой обязательной регистрации.
- Без скрытой телеметрии.
- Без автоматической отправки истории посещений.
- Хранить proxy credentials безопасно, используя подходящее системное хранилище секретов.
- Не записывать пароли в обычные логи.
- Не изменять VPN и firewall без разрешения.
- Не отключать kill switch.
- Не отправлять диагностические запросы вне VPN вопреки явной настройке пользователя.
- Предупреждать, что DIRECT-проверки могут раскрыть реальные IP и DNS-запросы целевым серверам.
- Ограничивать размер загружаемых ответов.
- Исключать localhost, loopback, link-local и частные адреса из удалённо управляемых проверок по умолчанию.
- Проверять перенаправления URL.
- Не выполнять произвольные shell-команды из пользовательских URL.
- Предоставить возможность удалить историю и экспортировать данные.

Для активных диагностических тестов используй разумные лимиты частоты и объёма трафика.

## 16. Обязательные тестовые сценарии

Система считается корректной, только если обрабатывает следующие случаи:

| Сценарий | Ожидаемое поведение |
|---|---|
| VPN выключен | DIRECT работает, VPN помечен недоступным |
| Включён системный HTTP proxy | Прокси-маршрут используется только предназначенными для него проверками |
| Включён SOCKS5 | VPN-маршрут проверяется через SOCKS5 |
| Включён TUN full tunnel | Не заявлять DIRECT без подтверждения обхода туннеля |
| TUN со split tunnel | Корректно учитывать разные маршруты |
| VPN разорвал соединение | Отобразить изменение состояния и ошибки |
| Kill switch блокирует DIRECT | Не пытаться скрыто обходить блокировку |
| IPv4 работает, IPv6 нет | Показывать отдельные статусы |
| Прокси доступен, конечный сайт нет | Отделять ошибку конечного ресурса от доступности прокси |
| DNS ошибается, TCP по IP работает | Указывать на вероятную DNS-проблему |
| DIRECT и VPN выходят через один IP | Не делать необоснованный вывод о маршруте |
| Нет интернета | Отобразить общий сетевой сбой, не объявлять массовую блокировку |
| API сервиса недоступен, сайт работает | Отобразить частичную доступность |
| VPN использует PAC с исключениями | Учитывать правила выбора прокси или показывать отсутствие поддержки |
| Изменился gateway во время проверки | Отметить измерение как потенциально недостоверное |

Создай воспроизводимые тесты с контролируемым mock server, локальным HTTP/SOCKS proxy и симулированными сетевыми ошибками, где это практически возможно.

Отдельно документируй сценарии, требующие настоящего Windows VPN/TUN окружения.

## 17. Критерии готовности MVP

Приложение должно:

1. Устанавливаться и запускаться на Windows.
2. Определять сетевые интерфейсы и системные прокси.

5. Независимо проверять DIRECT и VPN там, где это технически подтверждено.
6. Не выдавать VPN-трафик за DIRECT.
7. Сохранять результаты в SQLite.
8. Показывать таблицу доступности ресурсов.
9. Показывать графики истории.
10. Обновлять данные без перезагрузки интерфейса.
11. Корректно обрабатывать отключение интернета.
12. Давать объяснения сетевых ошибок.
13. Позволять добавлять собственные ресурсы.
14. Позволять настраивать интервалы проверки.
15. Не требовать собственного облачного сервера.
16. Иметь автоматические тесты.
17. Иметь рабочую сборку и инструкцию запуска.
